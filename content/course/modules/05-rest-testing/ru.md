# Тестирование REST API

REST API позволяют клиенту и серверу обмениваться ресурсами через HTTP. QA-инженер проверяет этот обмен на уровне контракта: метод запроса, endpoint, заголовки, тело, статус-код, схему ответа, правила данных, обработку ошибок и полезность диагностики.

## Ментальная модель REST

Ресурс удобно воспринимать как существительное, а HTTP-метод — как действие над ним.

| Метод | Типичный смысл | Пример endpoint | Фокус QA |
|---|---|---|---|
| GET | Прочитать данные | `/orders/123` | Статус, фильтры, права, форма возвращённых данных |
| POST | Создать данные или запустить действие | `/orders` | Обязательные поля, валидация, дубли, ссылка на созданный ресурс |
| PUT | Заменить ресурс целиком | `/orders/123` | Семантика полной замены, пропущенные поля, идемпотентность |
| PATCH | Изменить часть ресурса | `/orders/123` | Правила частичного изменения, неизменённые поля, конфликты |
| DELETE | Удалить ресурс | `/orders/123` | Авторизация, повторный вызов, связанные данные |

REST — это не только CRUD. Во многих API есть action endpoints вроде `/orders/123/cancel`. Проверяйте их как контракт поведения: какие входные данные допустимы, какой переход состояния происходит и какой ответ доказывает результат.

## Из чего состоит запрос

Запрос обычно включает:

- **Base URL и endpoint**: адрес сервиса и путь ресурса.
- **Метод**: `GET`, `POST`, `PUT`, `PATCH`, `DELETE` или другой HTTP-глагол.
- **Заголовки**: авторизация, content type, correlation id, локаль, настройки кэша.
- **Query parameters**: фильтрация, сортировка, пагинация, флаги.
- **Body**: JSON или другой формат данных для методов с телом запроса.

Пример:

```http
POST /v1/orders HTTP/1.1
Authorization: Bearer <token>
Content-Type: application/json
Idempotency-Key: 8f4b3f

{
  "customerId": "cus-104",
  "items": [
    { "sku": "BOOK-1", "quantity": 2 }
  ]
}
```

QA-вопросы:

- Какие поля обязательны?
- Какие значения невалидны, пусты, слишком длинны, дублируются или выходят за диапазон?
- Какая авторизация нужна?
- Что происходит при повторе того же запроса?
- Какие поля ответа являются стабильным контрактом, а какие только информационные?

## Из чего состоит ответ

Ответ обычно включает:

- **Status code**: общий результат запроса.
- **Заголовки**: content type, правила кэша, request id, ссылки пагинации, лимиты запросов.
- **Body**: JSON-данные или объект ошибки.

Семейства статус-кодов:

- **2xx успех**: `200 OK`, `201 Created`, `204 No Content`.
- **3xx redirect**: полезно для клиентов, но в JSON API встречается реже.
- **4xx проблема клиента или запроса**: `400 Bad Request`, `401 Unauthorized`, `403 Forbidden`, `404 Not Found`, `409 Conflict`, `422 Unprocessable Entity`, `429 Too Many Requests`.
- **5xx проблема сервера**: `500 Internal Server Error`, `502 Bad Gateway`, `503 Service Unavailable`, `504 Gateway Timeout`.

Сильная REST-проверка смотрит на сочетание, а не на одно поле. Например: отсутствие обязательного поля может вернуть `400` или `422`, но документация API должна определять конкретный вариант, а тело ошибки — помогать клиенту исправить запрос.

## Позитивные, негативные и контрактные проверки

Полезное покрытие API включает:

1. **Happy path**: валидный запрос, ожидаемый статус, ожидаемое тело ответа.
2. **Валидацию**: пропущенное поле, неверный тип, граничные значения, сломанный JSON.
3. **Авторизацию**: нет токена, неверная роль, истёкший токен, доступ к чужому ресурсу.
4. **Правила состояния**: отменить уже отправленный заказ, изменить закрытый тикет, повторить запрос перевода.
5. **Пагинацию и фильтры**: первая страница, пустой результат, большой размер страницы, неверный ключ сортировки.
6. **Идемпотентность и повторы**: повторить безопасный запрос и сравнить результат.
7. **Наблюдаемость**: request id, единый формат ошибок, понятные и безопасные сообщения.

## Postman и curl

Postman удобен для организации исследовательских запросов, примеров, окружений и лёгких assertions. `curl` удобен для передачи точного запроса текстом, быстрого воспроизведения случая и фиксации доказательств.

Пример curl-запроса:

```bash
curl -i -X POST 'https://api.example.test/v1/orders' \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer <token>' \
  --data '{"customerId":"cus-104","items":[{"sku":"BOOK-1","quantity":2}]}'
```

Когда фиксируете доказательство, включайте метод, endpoint, важные заголовки без секретов, тело запроса, статус и значимую часть ответа.

## Эвристики тест-дизайна для API

Для каждого endpoint соберите небольшую матрицу:

- Ресурс существует / не существует.
- У вызывающего есть доступ / доступа нет.
- Payload полный / неполный / сломанный.
- Данные обычные / граничные / экстремальные.
- Запрос первый / повторный.
- Сервис возвращает данные / подходящих данных нет.

Цель не в проверке всех комбинаций. Цель — выбрать комбинации, которые покрывают риск и объясняют, почему этот риск важен.

## Работа с AI-наставником

Просите наставника проверить ваше мышление по API, а не придумать идеальный чек-лист. Передайте фрагмент документации, свои предположения, выбранные запросы и доказательства. Попросите найти пробелы покрытия, неясные ожидаемые результаты и более удачную группировку проверок.

Сохраняйте ответственность за вывод. Если API-контракт неоднозначен, оформите неоднозначность как вопрос команде, а не делайте вид, что ожидаемое поведение известно.
