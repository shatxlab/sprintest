# Запуск тестов в CI

Набор тестов на Playwright, который запускается только у вас на ноутбуке, — личная привычка. Набор, который прогоняется на каждом пуше, — общая инфраструктура: тот, кто что-то сломал, узнаёт об этом через несколько минут и без вашего участия. Этот модуль о том, как перенести рабочий локальный набор в непрерывную интеграцию и не потерять по дороге то, ради чего он был нужен.

## Что меняет CI

Локально у вас накопилось состояние: установленные браузеры, прогретый кеш пакетов, тестовые данные, посеянные три дня назад, забытый запущенный dev-сервер. CI стартует с чистого клона на машине, которая ваш проект никогда не видела. Всё, на что набор тихо опирался, теперь нужно ставить явно.

Отсюда три следствия:

- **Headless — режим по умолчанию.** На раннере нет видимого окна, и тест, который прошёл только потому, что вы вовремя кликнули, — не тест.
- **Отчёт — единственный свидетель.** Перед машиной никто не сидит, поэтому HTML-отчёт, JUnit XML и трейсы и есть вся история прогона.
- **Ресурсы делятся между всеми.** У раннера меньше ядер и холоднее кеш, чем у вашего ноутбука, поэтому щедрые локальные таймауты и агрессивный параллелизм ведут себя иначе.

## Чтобы чистый клон заработал

Разрыв между свежей машиной и запускаемым набором закрывают две команды:

```bash
npm ci
npx playwright install --with-deps chromium
```

`npm ci` ставит ровно то, что зафиксировано в lock-файле — то сочетание версий, которое команда действительно проверяла. `npx playwright install --with-deps chromium` скачивает браузер **и** нужные ему системные библиотеки — те, что на вашем ноутбуке уже были. Пропустить `--with-deps` на раннере — классическая первая ошибка: браузер скачивается нормально, а потом падает при запуске из-за отсутствующей библиотеки.

## Файл workflow

Ниже — workflow для GitHub Actions, который прогоняет набор на каждом пуше и pull request и сохраняет отчёт как артефакт.

```yaml
name: playwright

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    timeout-minutes: 30
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npx playwright install --with-deps chromium
      - run: npx playwright test
      - uses: actions/upload-artifact@v4
        if: ${{ !cancelled() }}
        with:
          name: playwright-report
          path: |
            playwright-report/
            test-results/
          retention-days: 14
```

Читайте это как цепочку обещаний: забрать код, поставить известную версию Node с прогретым кешем пакетов, установить зависимости из lock-файла, поставить браузер, прогнать тесты, выгрузить доказательства. Строку `if: ${{ !cancelled() }}` забывают чаще всего: без неё упавший прогон не выгружает ничего, а отчёт нужен как раз тогда, когда тесты упали.

`timeout-minutes` — это страховка, а не цель. Если зависший браузер может держать задачу шесть часов, ваш пайплайн превращается в очередь, в которой ждут все.

## Репортеры: две аудитории

У прогона в CI два потребителя: человек, который разбирает падение, и платформа, которая показывает статус. Настройте обоих.

```ts
// playwright.config.ts
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './tests',
  fullyParallel: true,
  forbidOnly: !!process.env.CI,
  retries: process.env.CI ? 1 : 0,
  workers: process.env.CI ? 2 : undefined,
  reporter: process.env.CI
    ? [['list'], ['html', { open: 'never' }], ['junit', { outputFile: 'test-results/junit.xml' }]]
    : [['list'], ['html']],
  use: {
    baseURL: process.env.BASE_URL ?? 'http://127.0.0.1:4321',
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',
    video: 'retain-on-failure',
  },
  projects: [{ name: 'chromium', use: { ...devices['Desktop Chrome'] } }],
});
```

Что здесь стоит защищать:

- `html` с `open: 'never'` пишет самодостаточную папку отчёта и не пытается её отдать по сети. На раннере автоматически открытый отчёт может держать задачу до самого таймаута.
- `junit` даёт XML, который интерфейс CI разбирает в список тестов: ревьюер видит, какой именно тест упал, ничего не скачивая.
- `forbidOnly` роняет прогон, если в коммит просочился `test.only`. Сфокусированный тест, сжимающий набор до одного случая, — самый тихий способ потерять покрытие.
- `trace: 'on-first-retry'` записывает трейс только при проблеме: дёшево на успешном пути и полно на неудачном.
- `retries: 1` только в CI. Локально вам нужен честный первый результат.
- `baseURL` берётся из окружения, чтобы один и тот же набор мог смотреть и на локальную цель, и на развёрнутую.

## Трейсы: отладчик для CI

Отладчик к раннеру не подключить, а вот трейс скачать можно. В артефакте лежит по одному zip на каждый упавший тест; `npx playwright show-trace path/to/trace.zip` открывает таймлайн со снимками DOM, сетевыми запросами и консолью. Если трейс нужен с локального прогона, `npx playwright test --trace on` пишет всё подряд, а `npx playwright test --ui` — самый быстрый способ воспроизвести падение в живом окне.

## Держим прогон честным

**Ретраи прячут flaky-тесты, но не лечат их.** Один ретрай не даёт красному пайплайну блокировать команду из-за известного нестабильного теста, но у него должен быть план: воспроизвести через `npx playwright test --repeat-each=5`, починить причину или унести тест в карантин и удалить. Тест, который проходит со второй попытки, — дефект самого набора.

**Шардинг покупает время.** `npx playwright test --shard=1/3` запускает треть набора, поэтому матрица из трёх задач закрывается примерно за треть времени. Каждому шарду всё равно нужен свой браузер — кеш `~/.cache/ms-playwright` через `actions/cache@v4` с ключом по lock-файлу избавляет от повторной загрузки. И шардинг обнажает тесты, которые тихо зависели от порядка выполнения.

**Падения, которые живут только в CI,** обычно приходят из четырёх мест: абсолютный URL или зашитый порт там, где `baseURL` должен браться из окружения; таймаут, щедрый на вашем ноутбуке; тестовые данные или файл авторизации, которые были локально, но никогда не создаются в чистом клоне; и фиксированная пауза, которой на вашей машине просто хватало. Прежде чем чинить, классифицируйте падение: баг продукта, баг теста или проблема окружения. Разработчику как дефект уходит только первое.

## Чего не значит зелёный прогон

Зелёный означает, что тесты запустились и прошли, а не что они хороши. Тест без ассертов проходит вечно. Пайплайн, который никто не читает, хуже отсутствия пайплайна: он производит шум с видом авторитета. Ценность CI не в бейдже, а в привычке: красный прогон читают, классифицируют и в течение дня либо чинят, либо удаляют.

Соберите свой пайплайн в практической задаче этого модуля: вы пишете workflow, настраиваете репортеры и доказываете путь CI, прогнав набор headless так, как это сделал бы раннер.
