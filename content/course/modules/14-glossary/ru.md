# Глоссарий

Этот модуль — краткий двуязычный справочник. Используйте его, когда читаете задачи, пишете баг-репорты, просите AI-наставника о помощи или переводите между русским языком команды и английскими QA/IT-терминами.

Глоссарий — не скрипт. Значение слова может меняться от контекста, поэтому уточняйте смысл, если термин звучит расплывчато.

## Как работать с глоссарием через AI

- Просите наставника объяснить термин в контексте вашей текущей задачи.
- Просите два коротких примера: корректное употребление и частое недопонимание.
- В отчёте сначала ясно описывайте поведение продукта, затем полируйте терминологию.
- Если в команде привычен русский заимствованный термин, оставляйте его в скобках при первом упоминании.

## Базовые QA-термины

| English term | Русский / командный вариант | Простое значение |
| --- | --- | --- |
| Quality Assurance (QA) | обеспечение качества | Предотвращение проблем качества через процесс, ревью и тестирование. |
| Quality Control (QC) | контроль качества | Проверка, соответствует ли продукт заданным ожиданиям. |
| Requirement | требование | Описанная потребность, правило или поведение продукта. |
| Specification | спецификация, спека | Документ или источник, где описано ожидаемое поведение. |
| Test case | тест-кейс | Конкретная проверка с предусловиями, шагами, данными и ожидаемым результатом. |
| Checklist | чек-лист | Краткий список того, что нужно проверить. |
| Test design | тест-дизайн | Выбор того, что тестировать и как структурировать проверки. |
| Equivalence partitioning | классы эквивалентности | Группировка входных данных, которые ожидаемо ведут себя одинаково. |
| Boundary value analysis | анализ граничных значений | Проверка значений около краёв допустимых диапазонов. |
| Regression testing | регрессионное тестирование | Проверка, что изменение не сломало существующее поведение. |
| Retest | ретест | Повторная проверка конкретно исправленного бага. |
| Bug report | баг-репорт, тикет | Структурированное сообщение о дефекте или подозрительном поведении. |
| Severity | серьёзность | Влияние дефекта на пользователей или систему. |
| Priority | приоритет | Срочность или бизнес-порядок исправления. |

## Архитектура и эксплуатация

| English term | Русский / командный вариант | Простое значение |
| --- | --- | --- |
| Client-server architecture | клиент-серверная архитектура | Клиент запрашивает сервисы; сервер обрабатывает и хранит данные. |
| Monolithic architecture | монолит | Одно приложение, которое поставляется как единое целое. |
| Microservice architecture | микросервисы | Система из небольших независимых сервисов. |
| Message queue (MQ) | очередь сообщений | Компонент, где сообщения ждут обработки другим сервисом. |
| Producer | producer, отправитель | Сервис, который отправляет сообщения в очередь. |
| Consumer | consumer, обработчик | Сервис, который читает сообщения из очереди. |
| At-least-once delivery | доставка at-least-once | Гарантия очереди: сообщение может прийти более одного раза; потребители дедуплицируют по id. |
| Dead-letter queue | dead-letter очередь | Очередь для сообщений, обработка которых не удалась после разрешённых ретраев. |
| CI/CD | непрерывная интеграция и доставка | Автоматизация сборки, тестирования и выпуска. |
| DevOps | DevOps | Практики совместной работы разработки и эксплуатации. |
| DevSecOps | DevSecOps | Встраивание security-практик в процесс поставки. |
| Refactoring | рефакторинг | Улучшение структуры кода без изменения внешнего поведения. |
| Legacy | легаси | Старый код или системы, которые трудно безопасно менять. |
| Overengineering | оверинжениринг | Сложность выше реальной потребности задачи. |

## Проверка понимания

К любому термину задайте три вопроса:

1. Что он значит в этой задаче?
2. Какие доказательства покажут, что это работает или не работает?
3. Разработчик, тестировщик, продакт-менеджер и поддержка поймут его одинаково?
