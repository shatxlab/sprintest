# Playwright: читать и запускать

Ручное тестирование находит баг один раз. Автотест находит тот же баг при каждом изменении кода, на любой машине и без напоминаний. Именно поэтому в вакансиях automation QA всё чаще стоит фреймворк для браузерной автоматизации — и таким фреймворком стал Playwright.

Это первый из семи модулей про автоматизацию браузера, и начинается он с факта эпохи AI: ваш агент с удовольствием напишет черновик любого теста, который вы опишете. Но судьбу черновика решает тот, кто умеет его читать — кто запускает его, понимает каждую строку и отличает тест, который проверяет продукт, от теста, который просто проходит. Этот кто-то — вы, и чтение — навык, на котором стоит весь трек. Здесь вы поднимаете проект Playwright и учитесь читать тест — анатомию, локаторы, web-first ассерты, — запускать его и понимать, что прогон говорит на самом деле, когда он красный.

## Почему Playwright

- **Один API — три движка.** Один и тот же тест идёт в Chromium, Firefox и WebKit. Кроссбраузерность перестаёт быть отдельным проектом.
- **Автоожидание.** Каждое действие само дожидается, что элемент существует, виден, стабилен и активен. Ручные «подождать спиннер», из-за которых старые инструменты были хрупкими, встроены в движок.
- **Раннер в комплекте.** `@playwright/test` содержит раннер, ассерты, фикстуры, параллельный запуск, репортеры и trace viewer. Второй фреймворк прикручивать не нужно.
- **Node и TypeScript как основа.** Типы идут вместе с библиотекой, поэтому редактор подскажет, если вы вызвали несуществующее действие.

На разовую настройку закладывайте час. Дальше новый файл теста отделяют от запуска три строки.

## Каркас проекта

```bash
npm init playwright@latest
npx playwright install
```

Инициализатор создаёт конфиг, папку `tests`, пример спека и ставит браузеры. Всё дальнейшее живёт в `playwright.config.ts`:

```ts
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './tests',
  fullyParallel: true,
  use: {
    baseURL: 'http://127.0.0.1:4173',
    trace: 'retain-on-failure',
  },
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
  ],
});
```

Две настройки окупаются сразу. `baseURL` позволяет писать `page.goto('/')`. `trace: 'retain-on-failure'` записывает трейс для упавших тестов и выбрасывает его для прошедших — самая дешёвая страховка при отладке.

## Чтение теста

Когда агент отдаёт вам файл спека, первая работа — прочитать его как код, за который отвечаете вы. Возьмём такой:

```ts
import { test, expect } from '@playwright/test';

test('counter starts at zero', async ({ page }) => {
  await page.goto('/');
  await expect(page.getByTestId('counter-value')).toHaveText('0');
});

test.describe('sign-up form', () => {
  test('rejects an empty email', async ({ page }) => {
    await page.goto('/');
    await page.getByRole('button', { name: 'Create account' }).click();
    await expect(page.getByRole('alert')).toContainText('Email is required');
  });
});
```

Читаем по четырём частям. `test(...)` регистрирует одно поведение. Аргумент `{ page }` — это фикстура: Playwright выдаёт свежую страницу внутри свежего контекста браузера для каждого теста, поэтому тесты не наследуют состояние друг друга. `async` и `await` здесь не украшение: все действия в браузере асинхронные, и без `await` тест идёт дальше раньше, чем произошёл клик. `expect` — это проверка.

Читайте каждый файл от агента по двум привычкам:

- **Одно поведение на тест.** Тест, который одновременно регистрирует пользователя, проверяет счётчик и фильтрует список, покажет три несвязанные поломки одной красной строкой. Если агент так написал, это замечание к черновику, а не вкусовщина, которую можно стерпеть.
- **Имя описывает поведение, а не механику.** `test('counter starts at zero')` лучше, чем `test('counter test 1')` — отчёт превращается в читаемый список того, что умеет продукт. Механическое имя к тому же прячет, что тест поймает, а что пропустит.

## Как искать элементы — так же, как их описывает человек

Локатор — это способ теста дотянуться до элемента. Читая тест от агента, судите первым делом локатор: от него зависит, переживёт ли тест рефакторинг. Держите такой порядок:

```ts
await page.getByLabel('Email').fill('qa@example.com');
await page.getByRole('button', { name: 'Create account' }).click();
await expect(page.getByRole('alert')).toContainText('Email is required');
```

`getByRole` находит по accessibility-роли и имени — ровно то, что объявляет скринридер и по чему кликает человек. `getByLabel` связывает поле с видимой подписью. `getByTestId` — запасной вариант для элементов, которые пользователь никак не опишет; он переживает рефакторинг CSS, потому что не привязан ни к стилям, ни к структуре разметки. В следующем модуле этот словарь превратится в чек-лист ревью для тестов, написанных агентом; пока читайте длинную CSS-цепочку, в которой зашита вёрстка, как замечание к черновику, а не как стиль, который можно принять.

## Web-first ассерты и ожидание

Ассерты Playwright повторяют проверку, пока условие не выполнится или не истечёт таймаут:

```ts
await expect(page.getByRole('listitem')).toHaveCount(3);
await expect(page.getByTestId('status')).toBeVisible();
await expect(page.getByRole('button', { name: 'Save' })).toBeEnabled();
```

Поэтому в тесте не нужен код ожидания: `toHaveCount(3)` продолжает проверять, пока в списке не окажется три элемента или не пройдёт пять секунд. Читая тест от агента, требуйте прежде всего именно это: ассерты, которые сами дожидаются, и никаких `page.waitForTimeout(2000)` — фиксированная пауза либо слишком короткая (флак), либо слишком длинная (медленно), и она прячет настоящую причину нестабильности. Считайте её запашком, а не инструментом.

## Запуск и чтение результата

```bash
npx playwright test                       # everything, headless
npx playwright test signup                # only files matching 'signup'
npx playwright test --headed              # watch the browser
npx playwright test --ui                  # time-travel debugger
npx playwright test --repeat-each=3       # catch order and timing flakiness
npx playwright show-report                # HTML report from the last run
npx playwright show-trace trace.zip       # step through a recorded failure
```

Агент может отчитаться, что набор зелёный. Верьте прогону, а не отчёту: запустите сами и прочитайте сырой вывод — все команды выше понадобятся в первом задании.

Когда тест покраснел, задайте три вопроса по порядку: **сломался продукт, сломался тест или сломалась среда?** Неверный ассерт, который поймал корректное поведение, — это баг теста: правьте тест, а не заводите тикет. Верный ассерт против неверного продукта — настоящий баг: заводите его вместе с трейсом. Настоящий флак обычно означает общее состояние между тестами, потерянный `await` или фиксированную паузу.

## Что автоматизировать первым

Автоматизация — это инвестиция, и её отдача равна частоте, умноженной на риск. Первыми идут сценарии, которые прогоняются на каждой сборке и дорого стоят при поломке. Разовая миграция, экраны, которые перерисуют в следующем спринте, сторонние платёжные фреймы, на которые вы не влияете, и проверки, где нужен только человеческий глаз, пока обходятся дороже, чем экономят. Второе задание модуля как раз про то, чтобы принять такие решения на бумаге.

## Практика

Первое задание выдаёт вам страницу и набор тестов, написанные агентом: запустите набор, прочитайте каждый тест построчно, объясните, что он проверяет на самом деле, и внесите три небольшие правки. Второе — упражнение на приоритизацию, где нужно защитить выбор: что автоматизируем, а что осознанно оставляем человеку.
