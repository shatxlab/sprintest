# Отладка и flaky-тесты

Красный тест — это вопрос, а не приговор. Playwright записывает, что браузер сделал на самом деле, и ваша задача — ответить на этот вопрос до того, как вы измените хоть одну строку: это настоящий баг продукта, баг в самом тесте, проблема окружения или данных, или настоящая нестабильность? Классификация и есть навык. Исправление уже следует из неё.

## Сначала прочитайте вывод упавшего теста

Упавший прогон уже печатает почти всё, что нужно:

```
  1) cart.spec.ts:26:5 › promo code shows the discount › applies percent discount

  Error: expect(received).toHaveText(expected)

  Expected string: "-10.00"
  Received string: "0.00"

  Call log:
    - expect.toHaveText with timeout 5000ms
    - waiting for locator('[data-testid="discount"]')
    - locator resolved to <span data-testid="discount">0.00</span>
    - unexpected value "0.00"

    24 |   await page.getByRole('button', { name: 'Apply' }).click();
    25 |
  > 26 |   await expect(page.getByTestId('discount')).toHaveText('-10.00');
```

В этом блоке три факта: что ожидали, что приложение реально отдало и где это произошло. Недооценённая часть — call log. Он показывает, нашёл ли локатор элемент вообще и во что именно он разрешился. Локатор, который не нашёл ничего, и локатор, который нашёл не то значение, — это разные падения и разные ответственные.

## Включите интерактивные инструменты

Замедлите прогон и посмотрите, как работает браузер:

```bash
npx playwright test --debug                 # Inspector: шаг за шагом, можно пробовать селекторы вживую
npx playwright test --debug cart.spec.ts
npx playwright test --debug --last-failed   # только тесты, упавшие в прошлом прогоне
```

Внутри теста `await page.pause()` открывает тот же Inspector на нужной строке. Режим `--debug` интерактивный: его место на вашей машине, а не в закоммиченном тесте.

Для захваченного прогона без окна браузера:

```bash
npx playwright test --trace on
npx playwright show-trace test-results/<test-name>/trace.zip
```

## Trace viewer: бортовой самописец

Пишите трейсы там, где они нужны — они тяжёлые. Обычная настройка для CI:

```ts
// playwright.config.ts
import { defineConfig } from '@playwright/test';

export default defineConfig({
  use: {
    trace: 'retain-on-failure',      // 'off' | 'on' | 'retain-on-failure' | 'on-first-retry'
    screenshot: 'only-on-failure',
    video: 'retain-on-failure',
  },
  retries: process.env.CI ? 2 : 0,
});
```

`retain-on-failure` сохраняет трейс для каждого упавшего теста и выбрасывает трейсы успешных — правильный вариант по умолчанию для CI. Трейс даёт прокручиваемую по шагам шкалу: каждое действие со снимками DOM до и после, сетевые запросы со статус-кодами, сообщения консоли, исходники страницы и точный локатор каждого действия.

Откройте `trace.zip` и идите в таком порядке:

1. Перейдите к упавшему шагу и посмотрите снимок **Before**. Элемент вообще был в DOM?
2. Проверьте сетевые строки этого шага. Запрос вернул 4xx или 5xx — или не ушёл вовсе?
3. Прочитайте консоль: не было ли необработанной ошибки до ассерта.
4. Посмотрите локатор во вкладке исходников. Если он нашёл несколько элементов, снимок покажет, какой из них победил.

## Flaky-тесты: падение, которое не повторяется

Flaky-тест проходит и падает на одном и том же коде. Это дефект набора тестов, а не повод перезапустить прогон. Retries — измерительный прибор и временный щит: они превращают жёсткое падение в мягкое и никогда не чинят причину. Соберите их статистику, посчитайте, исправьте.

Обычные причины, примерно по частоте:

- **Гонки.** Ассерт срабатывает раньше, чем приложение устоялось. Честное исправление — web-first ассерт, который сам повторяет проверку: `await expect(page.getByRole('status')).toHaveText('Saved')` опрашивает до таймаута. Фиксированный `page.waitForTimeout(2000)` делает прогон медленнее и всё равно падает на загруженной машине.
- **Зависимость от порядка.** Один тест меняет данные, от которых зависит другой. Симптом: по отдельности всё зелёное, весь файл целиком — красный. Запустите `npx playwright test --workers=1` и увидите, как падения выходят наружу.
- **Общее изменяемое состояние.** Переменные уровня модуля, одна общая учётная запись, засеянная строка, которую тест удаляет.
- **Коллизии данных.** Два теста занимают один и тот же email или ID, параллельные воркеры дерутся за одну запись.
- **Время и локаль.** Тест проверяет сегодняшнюю дату или формат валюты и числа, которого никто не обещал.
- **Анимация.** Компонент в середине перехода не кликается. Ждите состояние, а не часы.

## Протокол разбора, который выдержит ревью

1. **Воспроизводите осознанно.** `npx playwright test --repeat-each=5` — для подозрения на flakiness, `--last-failed` — чтобы после правки прогнать только падения, `--workers=1` — чтобы отделить эффект порядка от настоящих гонок.
2. **Не перезапускайте до зелёного.** Зелёный перезапуск без диагноза — это отложенный баг-репорт.
3. **Классифицируйте, опираясь на доказательства.** Баг продукта, баг теста, проблема окружения или данных, зависимость от порядка — и назовите, что именно решило: снимок, статус запроса, строка консоли, строка исходника.
4. **Чините на правильном уровне.** Настоящий баг продукта становится баг-репортом с приложенным трейсом. Баг теста — это исправленное ожидание или локатор. Проблема окружения — это фикстура и засев данных, которые не врут.
5. **Проверьте, что исправление падает по правильной причине.** После правки теста сломайте приложение намеренно и убедитесь, что тест краснеет. Тест, который проходит, ничего не проверяя, хуже flaky-теста.

## Как оформить падающий тест

Пишите для разработчика, который не запускает ваш набор:

- имя теста, файл и строка, команда для воспроизведения;
- классификация и доказательства, на которых она построена;
- путь к файлу трейса или вставленный фрагмент: нужный снимок и строка запроса;
- для бага продукта: ожидаемое, полученное и минимальное воспроизведение;
- для бага теста: что проверял тест и что продукт на самом деле обещает.

## Что пригодится в практической задаче

В практической задаче в вашем собственном репозитории сгенерируется маленькое приложение с заложенной проблемой тайминга и четырьмя падающими тестами Playwright. Одно падение — настоящий баг продукта, одно — неверное ожидание, одно — проблема окружения или данных, и одно падает только при запуске файла по порядку. Разберите все четыре по трейсам, исправьте каждое на своём уровне и докажите каждое исправление.
